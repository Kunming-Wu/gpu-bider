gpu-bidera polite GPU job queue

It waits for the card, starts the next experiment the moment it is free, and never touches anybody else's process. Built for the shared box where four people want one GPU and nobody has root. 

# install
pipx install git+https://github.com/wkmallmx/gpu-bider
The problem

Two people who both check first still collide

A decision is not visible in nvidia-smi until seconds later. Nothing in a naive polling loop covers that gap — and the failure mode is not a slow job, it is a dead one.

Two naive watchers
alice3 GB
bob3 GB

Both see a 5 GB gap, both conclude their 3 GB task fits, both start. 6 GB into a 5 GB hole.

One of them dies with a CUDA OOM — and it was the tool that caused it, so it gets uninstalled.

Two biders
alice3 GB
bobwaits

Alice writes a claim before starting. Bob's decision subtracts it, sees 2 GB left, and declines.

Bob waits on purpose — and starts the second the card is genuinely free.

1

It never touches another process

No signals, no preemption, no killing. If somebody else is running, it is simply not your turn yet. There are exactly two call sites that can stop anything, and both act only on pids bider itself started.

2

Waiting is queued, not raced

A claim is written before anything starts, so two people cannot both decide the same free card is theirs. The loser re-evaluates on the next tick — it costs a poll, never a job.

How it decides

Five gates, in order. The first one that says no wins.

Every refusal carries its reason, and the reason is what you get back — in probe, in status, and in the payload the watcher prints.

  1. memory A colleague flagged as not-to-be-disturbed is on the card, or a reserved window is in force. hard block
  2. claims Live reservations by other bider instances are subtracted from what the card reports as free. hard block
  3. capacity After the task's own appetite, is enough left for the desktop? Memory and utilization both. hard block
  4. first fit If the head of the queue does not fit, try the next task rather than stalling everything behind it. routing
  5. intent Somebody registered for the same room before us. Stand down rather than race for the last gigabyte. courtesy

The reserve

By default 2 GB and 25% are held back from every task, because on most of these boxes the GPU is also driving the display. That is why a 5 GB task will not start on a 6 GB card even when the card looks idle — by design, not by bug.

Run order

Pinned first, then explicit rank, then cheapest first — ascending gpus × vram × util. A thirty-second smoke test should not sit behind a six-hour training run. Profiles bias it further; pin always wins.

One directory, and everybody is coordinated

claims/

        

          One file per job, with a TTL. Two colleagues starting at the same
          instant cannot both win. A claim whose process died is dropped after a
          short grace period, so a crash cannot hold the card hostage.
        

      

      

        
memory/

        

          What each person has published about their own needs. You can see that
          Wei has a deadline this week, and stay out of its way — which is the
          whole point of putting a tool on a shared machine.
        

      

      

        
intent board

        

          bider intent publish says “I am waiting for 5 GB.” Read-only
          to others, and it never blocks anybody by itself. People who never
          publish still appear, as claims, once they start.
        

      

    

  







  

    

      Memory
      
What the machine knows about the others

      

        The most useful part, and the reason this is more than a polling loop.
        These entries outrank every heuristic.
      

    


    

      
      
      
    


    

      

        
Never disturb this person's processes. It applies only while one
          of them is actually on the card — when they are not running you
          are free to use the machine, and the entry survives so a later session
          still knows about them.

        
    
          
  • --until lets it lapse on its own, so a
            “deadline this week” flag does not become a permanent claim.
    • 
          
  • --task scopes it to one of your own runs.
    • 
          
  • --private keeps it out of the shared directory.
    • 
        

        

          
bider memory --protect wei --match loro_train \
      --because "deadline this week" --until 2026-10-22

          
        

      


      

        
Recurring time reserved for someone, possibly crossing midnight.
          The watcher will not start a task inside one, and will not begin a run
          in the last few minutes before one opens — there is no point starting a
          two-hour job at 13:55 before a 14:00 reservation.

        
    
          
  • Crosses midnight with --from 22:00 --to 02:00.
    • 
          
  • Weekday-aware: --days mon-fri, or
            sat,sun, or a wrapping fri-mon.
    • 
          
  • Honest limit: without preemption a window can only stop bider
            from occupying the card. It cannot make a running job stop.
    • 
        

        

          
bider memory --window wei --from 14:00 --to 18:00 --days mon-fri

          
        

      


      

        
How a process family behaves. --vram heavy --util light
          describes something that holds memory but barely computes — so the queue
          is reordered toward tasks shaped the opposite way, and the two jobs
          coexist instead of contending.

        
    
          
  • Advice, not a veto. It biases ordering; pin and
            rank still win.
    • 
          
  • --suggest promotes a family to a profile only
            after several polls agree, and marks it
            "source": "observed" — so you can tell evidence from a
            statement.
    • 
        

        

          
bider memory --profile train --profile-vram heavy --profile-util light
bider memory --suggest   # learn shapes from what it has seen

          
        

      

    

  







  

    

      

        Explain a wait
        
“Why hasn't my job started?”

        

          The question every scheduler gets asked, answered in prose with the
          numbers behind it: the reserved window, the protected colleague, the
          shortfall, who holds the card, who registered first.
        

        

          
$ bider explain
Task 'lr-sweep' wants 3.50GB and 60% of the card, and has been waiting 22 min.
It cannot start yet:
  - wei is running and is protected (deadline this week).
    Waiting for it to finish is the point.
  - free 5.85GB - need 3.50GB = 2.35GB < reserve 2.00GB

          
        

      


      

        Estimate a finish
        
How much longer will that take?

        

          Reads the log tail, matches tqdm bars, 21/50,
          Epoch 3/10, step 250/1000 and bare
          percentages, then projects from the rate the number is moving at
          now — discarding samples from before a restart.
        

        

          
$ bider estimate --pid 12345 --log job.log --json
{
  "progress": { "current": 340, "total": 1000, "percent": 34.0 },
  "eta_s": 1440, "eta_human": "24m00s",
  "basis": "progress 210 -> 340 over 300s (26.00%/min, 6 samples)"
}

          
        

        

          No progress marker means no ETA.
          It returns null and says what it looked for, rather than
          guessing.
        

      

    

  







  

    

      Limitations, stated plainly
      
What this cannot do

      

        Written down because a scheduler you cannot reason about is worse than no
        scheduler. Every one of these is a design decision, not a bug report
        waiting to happen.
      

    


    

      

        Windows/WDDM reports [N/A] for per-process GPU memory.
        Bider therefore never attributes memory to a process. It diffs whole-GPU
        totals and diffs the set of compute PIDs — both reliable. On Linux, NVML
        does report per-process memory and estimates get better.

      

        Inside a container, pid attribution can be wrong. nvidia-smi
        may report host pids. Protected-process matching then fails open:
        it will not block.

      

        A shared directory over NFS has unreliable locking. Claims are
        TTL-based as well as locked, so a lost race costs a duplicate write and a
        re-evaluation — never a stuck card.

      

        Pids get reused. A claim guards against it with a TTL and a liveness
        check; a very unlucky reuse could still mislead a protected-process
        match.

      

        Utilization is not a reservation. Two jobs each claiming 50% do not
        cleanly share a card — they contend. The util figure is a politeness
        margin, not a partition. Real isolation needs MIG or MPS, which is a
        different tool.

      

        Nobody is obliged to use this. Someone who has never heard of bider
        can start a job whenever they like. Bider is built to lose gracefully when
        that happens.
